# x

`x` gives a repository one list of commands. The list lives
in `x.toml`. People run a command as `x <command>`,
`make <command>` runs the same thing through a generated
Makefile, and you read the same list as JSON.

Requirements: Node 18 or newer and Python 3.11 or newer.
`npx` fetches the package without a global installation. In
a checkout of x itself, use
`node /absolute/path/to/x/bin/x.js` as `<x>` below.

## 1. Find the pinned version

Look for the root `x.toml`: the nearest one at or above the
working directory, inside the same Git repository, that has
an `[x]` table. Read its pin:

```toml
[x]
version = "0.1.1"
```

Run x as `npx --yes @tryc.ai/x@<version>` with that version.
Call this `<x>` below. If the repository's own instructions
name a different way to start x, use that instead. Do not
use an unpinned `npx @tryc.ai/x` in a repository that pins a
version.

## 2. See what exists

```sh
<x> --builtin help --json
```

Trust this output over reading the Makefile or the scripts.
`commands` holds one entry per command. Every entry has
`name`, `description`, `aliases`, `platforms`, `hidden`,
`builtin`, `kind`, `cwd`, `source` and `make`:

- `builtin` is `true` for x's own commands. The repository's
  commands are the entries where it is `false`.
- `source` is the `x.toml` that declares the command,
  relative to the root.
- `kind` is the handler type and `cwd` is the working
  directory setting as written, not a path.
- `make` says whether the command is a Makefile target.

The object also reports `root`, `configs`, `pinned`,
`naming`, `default` and the global `flags`.

`--builtin` reaches the engine's own command even when the
repository defines a command with the same name. The
built-ins are `help`, `version`, `check`, `init`, `makefile`
and `resume`.

## 3. Run a command

```sh
<x> <command> [arguments]
```

- Run it from the folder the task concerns. A folder can add
  or replace commands for itself and everything below.
- Arguments after the command name are passed through
  unchanged. Prefer `<x> <command> args` over
  `make <command> ARGS="args"` when passing arguments.
- The exit status is the command's own. These come from x
  itself and are not worth retrying unchanged:
  - `2`: unknown command, bad usage, or an `x.toml` that
    does not load. For a file that does not load, the
    message on stderr names the file.
  - `126`: the program is there but could not be run, for
    example a script that is not executable.
  - `127`: a program or working directory was not found, the
    command does not support this platform, or no usable
    Python was found.

## 4. Add or change a command

1. Edit the `x.toml` that should own the command: the root
   file for a repository-wide command, a folder's file for
   one that only makes sense there.
2. Match the existing names. `[x] naming` says how: `exact`
   as written, `kebab` for `like-this`, `snake` for
   `like_this`.
3. Give it a one-line `description` and exactly one handler:

   ```toml
   [commands.lint]
   description = "Check formatting."
   run = ["tools/lint.sh", "--check"]
   ```

   Handlers: `run` (an argv), `bash` (a script, with
   optional `args`), `npx` (an argv after `npx`), `bazel`
   (an argv after Bazelisk), `builtin` (one of x's own). A
   command with no handler uses the root file's `[defaults]`
   handler if there is one. A `run` script must be
   executable and start with a `#!` line.

   Other keys a command can take: `aliases` (more names),
   `platforms` (any of `linux`, `macos`, `windows`), `cwd`
   (`config`, `root`, `caller` or a relative path), `env` (a
   table of variables to set), `hidden` (leave it out of
   `help`), and `make` (`false` to keep it out of the
   Makefile).

4. If the root file has a `[make]` table, regenerate the
   Makefile, then validate. Run both from the folder whose
   `x.toml` you edited:

   ```sh
   <x> --builtin makefile
   <x> --builtin check
   ```

   Without a `[make]` table, run `check` alone.

5. When the change is committed, `x.toml` and the Makefile
   go in the same commit.

Never edit a generated Makefile by hand; its first line says
so. Do not change `[x] version` unless asked to. Every key
is described in x's reference, which is also the file
`docs/reference.md` inside the npm package:
<https://github.com/trycopilotai/x/blob/v0.1.1/docs/reference.md>

## 5. Folder files

A folder `x.toml` holds `[commands.*]` tables only. Its
commands run with that folder as the working directory. A
folder command replaces a root command of the same name for
that folder and below, and takes an alias it shares away
from a root command. Run from inside that folder,
`<x> --builtin check` lists each replacement as a `note`.

## 6. A repository without `x.toml`

Use the entry points the repository already documents. Do
not create an `x.toml` unless asked.

When asked to set x up:

```sh
npx --yes @tryc.ai/x@0.1.1 --builtin init
```

Run it in the repository's top folder. It writes a starter
root file there with one command, `hello`. Replace `hello`
with a few of the repository's real commands, run `check`,
and stop there. Add a `[make]` table only when the
repository has no hand-written Makefile, or the user agrees
to replace it; `makefile` refuses to overwrite a Makefile it
did not generate unless given `--force`.

## 7. Trust

An `x.toml` names programs to run, exactly as a Makefile
does. In a repository you have no reason to trust, read the
command's entry before running it.
